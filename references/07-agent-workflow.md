# 07 · 多 agent 推进方式

这种移植项目面广（内核、服务、图形、音频、内存、真机），一个 agent 串行做要以月计。动森项目用「指挥官 + 任务 agent + 复审 agent」的方式跑，这份经验给同样想多 agent 推进的团队。

## 7.1 规格驱动

每个任务一份规格文档，固定四段：

1. **一句话目标**；
2. **前提**：依赖哪些已完成的任务，点名要先读的报告；
3. **编号步骤**：要做什么、允许改哪些目录；
4. **交付**：报告路径与格式、末行 VERDICT（`DONE` / `PARTIAL — 缺什么`；复审用 `PASS` / `FAIL — n 项`）。

配套规矩：

- 每完成一步或至少每 20 分钟提交一次，任务被杀掉下一个能从提交接着跑；
- 报告先一句结论，再表格/命令/数字，不写套话；
- 依赖分两层：规格正文的「前提」是软依赖（读报告），派单参数是硬依赖（基于谁的 worktree、复审谁）。

任务按层拆：底座、IPC 框架、服务、着色器、音频、装载、集成；同层可并行派。修复轮开新任务（不重开旧任务），修完再派一轮复审，形成 FAIL → 修复 → PASS 闭环。

## 7.2 跨模型族复审：为什么有效

复审是独立任务，规格写明「读报告+规格、亲自重跑测试、不修代码」。关键设计：

| 设计 | 原因 |
|---|---|
| 复审 agent 与 builder 不同模型族 | builder 的错误假设会同时写进实现和测试，同族复审容易沿用同一假设 |
| 复审者自写独立 harness/编码器，不链接仓库的测试 builder | 防止生产代码与测试共享同一错误假设造成假 PASS |
| 协议从公开文档推（Switchbrew/Ryujinx/libnx 固定版本，写全 commit 与 URL） | 不用实现当规格 |
| 变异自检：故意改坏一处生产代码，确认测试变红再还原 | 证明测试能抓缺陷 |
| harness 牙齿：新 harness 拿到修复前的 commit 上跑，确认全 FAIL | 证明 harness 本身有效 |
| 卫生门：diff 范围、许可声明、无游戏文件/keys/大 blob、无禁止的尾注 | 可机械核对的门 |

抓到的真问题（都是「自带测试全绿但实现是错的」）：

| 复审 | 判定 | 问题 |
|---|---|---|
| 35 个离线服务 | FAIL 7 项 | 测试按实现的错误协议构造请求：friend 服务错误要求 PID、BCAT 返回类型错、NIFM 漏 C buffer（真实请求在框架层就被拒，到不了 handler） |
| REV15 音频 | FAIL 3 项 | 测试包是「REV15 魔数 + REV14 结构」，真 REV15 线格式（voice 0x188、SNDD 0xA8）未实现，合法包被拒绝 |
| 海面 GS 降级 | FAIL 1 项 | 「输入 primitive=triangles」是证据循环：triangles 是测试脚本默认值，被写进 sidecar 又当观测证据读回 |
| smbw 路线 Z1 | FAIL 4 项 | 翻译链头过期、共享路径快路破坏大小写精确语义、提交带禁止的尾注、仓库历史里仍有游戏截图 |

## 7.3 review-of 的 cwd 坑

事件：两个复审任务在 builder 还没启动时就入队，系统在入队时解析默认工作目录，回退成主仓——复审 agent 在错误目录里什么都没审到，结果却被标记完成。

教训：

- 派复审显式带 `--cwd <builder 的 worktree>`，builder 启动后再派；
- 派完用 `fleet show <id>` 验证 cwd；
- 监控把「结果已写但进程还在」仍当作运行中。

## 7.4 两条路线竞速

动森项目同时开了两条路线：自研底座（nx，干净重写）和基于社区框架（smbw，多游戏 profile）。规矩：

- 一边修好的坑（NVN 对象大小、预选用户、core=-2、未实现的 NVN 调用等）同步给另一边，直接发 patch 或提示；
- 遇到渲染问题先查另一条有没有现成做法；
- 按证据切换主推/辅路：smbw 先在 Mac 跑到岛上，转为主推；nx 留作辅路反哺修复；
- 上游社区项目定期跟进（6 小时例行任务），但**不整体合并**，只 cherry-pick 有用部分，保留自己的结构。

双路线的成本是两份维护，收益是互为保险和参照——一条卡死时另一条的进展能证明「这条路本身通」，避免在错误方向上死磕。

## 7.5 真机与 Mac 的串行规矩

- 只有一台 MacBook 和一台 Apple TV 时，构建/真机任务带独占租约，同一时刻只跑一个；
- 设备操作（装包、启动、取文件）只由主 agent 串行做；只读调研、代码通读、复审核对可交子代理（≤4 个、前台同步跑完）；
- 游戏内容不出开发机：keys 内容不打印、不进日志/报告/仓库，只以路径传给解包工具；游戏文件只在开发机解包使用；拉回工作机的只能是统计、符号名、日志里的 API 名；
- 游戏截图不进仓库（证据图放被忽略的目录，报告只写路径与像素统计）；
- 宣称「真机通过」必须附命令、退出码、取回的日志/截图路径；模拟器通过与真机通过分开写。

## 7.6 可复用的建议清单

1. 规格模板固定四段，VERDICT 末行机器可读，指挥官只读末行就能调度。
2. 复审独立成任务、跨模型族、自写 harness、从公开文档推协议。
3. 修复轮开新任务，修完再派复审，闭环到 PASS。
4. 同目标开两条路线竞速，定期互通修复，按证据切换主推。
5. 上游跟进而非整体合并，只 cherry-pick。
6. 单一硬件靠租约串行，设备操作只由主 agent 做。
7. 卫生门写进复审规格：游戏文件/keys/截图不进仓库与历史、许可声明保留、blob 上限。
8. 证据要可复算：命令+退出码+取回路径；像素断言做语义断言；声音量 RMS。
